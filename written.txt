a. Put every point in a tiny square near one corner, say [0, 1/256] x [0, 1/256]. At the root they all fall into the same child, and that repeats at every level, so the tree becomes one long chain and all the points end up in a single leaf - effectively a list (ignoring any depth cap, which only limits how long the chain gets). A tiny query box around the opposite corner, e.g. around (1, 1), touches only empty cells and finishes in constant time no matter how many points were inserted. A query that overlaps the crowded corner leaf has to report every point in it, and since all n points sit there, that takes O(n).

b. The duplicate is simply inserted again each time, so a leaf that is supposed to hold at most 8 points keeps growing past 8 instead of being split into more useful pieces. Once the leaf is at the deepest allowed level it cannot split any further, so it collects all n copies and every query touching that spot costs O(n). The simplest fix is to avoid storing duplicates - keep a count per point, or check before inserting - and otherwise to cap the depth and let a crowded leaf use a different container, like a counted list.

c. A quadtree is tied to fixed, axis-aligned world coordinates, so it does not move with the scene. Translating everything is cheap only if you move the root box along with it, since then each object stays in the same relative cell; without that, objects near cell edges change cells and the structure has to be rebuilt or reinserted. Rotating the scene is worse: the splits are axis-aligned, so rotated objects get bigger axis-aligned boxes, more of them cross the centre lines, and they get pushed up into the shared lists of high-level nodes, making queries much more expensive. So quadtrees suit static or slowly moving, roughly uniform, axis-aligned scenes, and are a poor fit for scenes that are rotated or transformed as a whole.
